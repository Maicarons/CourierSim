# 国际化（i18n）架构

CourierSim 首发支持 **简体中文（zh_CN）** 与 **English（en_US）** 两种语言，玩家可在主菜单与游戏内随时切换，选择会被持久化，下次启动自动恢复。

本文档说明 i18n 的整体设计、关键文件、运行时切换机制，以及如何为新内容添加翻译。

## 设计原则

游戏里需要翻译的文本分两类，采用**混合方案**：

1. **UI 框架文本**（按钮、面板、提示、状态名、枚举名等）
   — 字符串数量多、与代码强耦合，集中放在一张 `strings.json` 键值表里，通过 `Localization.t(key)` 取用。
2. **专有名词**（区域名、城市名、科技名、事件名等）
   — 这些本身就是数据，就近放在各自的数据 JSON 里，用 `*_en` 字段存储英文，由对应类的 `display_name()` / `display_desc()` 方法按当前语言返回。

这样既不破坏数据文件的自洽性，又让 UI 文案与代码解耦、便于整体翻译。

## 核心组件

### `src/autoload/Localization.gd`

全局单例（Autoload，注册名即 `Localization`），负责：

- 启动时加载 `res://src/i18n/strings.json`；
- 提供 `t(key: String) -> String` 取当前语言文案；
- `set_locale(code)` 切换语言并广播 `locale_changed` 信号；
- `is_en()` 供专有名词方法判断是否英文模式；
- 通过 `ConfigFile` 把选择持久化到 `user://settings.cfg`。

**回退链**：当前语言缺该 key → 回退默认语言 `zh_CN` → 再缺失则返回 key 本身（便于排查漏翻）。

> ⚠️ 注意：该脚本**不能**写 `class_name Localization`，否则会与同名的 Autoload 单例冲突，导致 `Localization` 被解析成类类型而非单例实例，所有 `Localization.t(...)` 调用都会报 "Cannot call non-static function"。

### `src/i18n/strings.json`

两层结构，顶层为语言码，下层为 `key → 文案`：

```json
{
  "zh_CN": {
    "menu.start": "开始游戏",
    "toast.welcome": "欢迎来到 %s，%s！"
  },
  "en_US": {
    "menu.start": "Start Game",
    "toast.welcome": "Welcome to %s, %s!"
  }
}
```

支持的占位符与 GDScript 的 `%` 格式化一致（`%s` / `%d` 等），由调用方传入参数。

## 专有名词的 `*_en` 字段

各数据类在中文名之外增加英文/描述字段，并提供 `display_*()`：

| 类 | 字段 | 显示方法 |
| --- | --- | --- |
| `City` | `name_en` | `display_name()` |
| `Region` | `region_name_en`（JSON 中为 `name_en`） | `display_name()` |
| `TechNode` | `tech_name_en` / `description_en` | `display_name()` / `display_desc()` |
| `EventData` | `name_en` / `desc_en` | 事件提示按语言取用 |

`display_name()` 的语义：

```gdscript
func display_name() -> String:
    if Localization.is_en() and name_en != "":
        return name_en
    return name
```

区域数据（`src/map/data/regions/*.json`）在根节点与每个城市节点都加了 `name_en`；科技数据（`src/data/tech.json`）每个科技加了 `name_en` 与 `desc_en`。

## 运行时切换

- **主菜单 `MainMenu.gd`**：语言 `OptionButton`（中文 / English）。切换时 `Localization.set_locale(...)` 广播 `locale_changed`，菜单重建 UI 树并保留已输入的Company 名与所选模式。
- **游戏内 `GameScene.gd`**：顶栏语言按钮切换。收到 `locale_changed` 后重建 UI (`_build_ui()`)、恢复当前 Tab (`show_tab(current_tab)`) 并刷新顶栏 (`refresh_top()`)。
- **系统层**：所有提示（toast）、目标（objective）文本统一走 `Localization.t(...)`；城市/区域/科技列表统一用 `display_name()`。

## 持久化

语言选择写入 `user://settings.cfg` 的 `[i18n] locale`。`Localization._ready()` 启动时调用 `_apply_saved()` 读回，并同步 `TranslationServer.set_locale(code)`。因此玩家关闭游戏后再次进入会自动沿用上次语言。

## 如何新增翻译

### 1. UI 框架文本

在 `strings.json` 的两个语言表下加同一个 key（建议用点分命名空间，如 `panel.warehouse.title`）：

```json
"zh_CN": { "panel.warehouse.title": "仓库管理" },
"en_US": { "panel.warehouse.title": "Warehouse Management" }
```

代码里用 `Localization.t("panel.warehouse.title")` 取用。漏翻时界面会显示 key 本身，方便定位。

### 2. 专有名词

在数据 JSON 的对应节点补 `*_en` 字段，并确保对应类已有 `display_*()` 方法（见上表）。界面统一通过 `display_*()` 取显示名，无需改动调用处。

> 新增语言（如 `ja_JP`）只需：在 `strings.json` 加顶层表、在各数据类补齐 `*_en` 对应语种字段、并把这些语言码加入 `Localization.SUPPORTED`。

## 验证

i18n 层已通过运行时断言验证（headless 场景临时脚本，验证后已删除），覆盖：

- `zh_CN` 默认返回中文、`en_US` 返回英文；
- 缺失 key 回退链正确返回 key 本身；
- `is_en()` 随语言切换正确翻转；
- `City` / `Region` / `TechNode` 的 `display_name()` / `display_desc()` 在两种语言下均返回正确文本。

引擎编译校验（`godot --headless --editor --quit`）零 `SCRIPT ERROR`，启动无 `push_error`。
